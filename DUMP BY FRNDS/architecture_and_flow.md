# Botzilla AI Meeting Summarizer Architecture & Flow

This document outlines the complete lifecycle of a video upload in the Botzilla app and explains the underlying architectural choices, including the external slide generation dependency.

---

## 1. Why The External Slide Pipeline (VTT & Grid Stitching) is Inefficient

In `ApplicationCodeFile/vedio_processor.py`, the external team implemented a "Sprite Sheet" approach for handling slides. 

### What it does:
1. **Scene Detection**: Runs FFmpeg smart scene detection to extract individual frames when the visual changes significantly (`select='isnan(prev_selected_t)+gte(t-prev_selected_t,7)+gt(scene,0.02)'`).
2. **Image Grid Stitching**: Takes all those extracted frames and stitches them together into a single massive PNG grid image (`tile=10xN`) using FFmpeg (Lines 263-269).
3. **VTT Map Generation**: Generates a `.vtt` file mapping timestamps to `x,y,w,h` coordinates on that giant grid image (Lines 278-292).

### Why this is inefficient for our architecture:
Our goal is to generate a **Word Document (.docx)** with high-quality inline images. 

* **The Sprite Sheet Problem**: A Word document needs individual image files to insert into the document layout. It cannot display "a cropped section of a giant sprite sheet" natively. 
* **Wasted Compute**: Because the external pipeline forces the individual frames into a grid, we have to run a reverse process (`run_botzilla_local.py` -> `extract_slides_ffmpeg()`) that parses the `.vtt` map and uses FFmpeg to *crop those images back out* of the grid into individual files so `docxGenerator.ts` can use them.
* **Resolution Limits**: Stitching a grid of 640x360 images quickly hits the maximum pixel dimensions of image formats (e.g., FFmpeg's 32767 pixel limit, handled dynamically on lines 258-260).
* **Network/Memory Overhead**: If we send this to a frontend, loading one massive 50MB PNG file just to show a few slides is much heavier than loading individual 100KB JPEGs on demand.

**Conclusion**: While WebVTT sprite sheets are a clever trick for HTML5 video scrubbers (like YouTube's preview thumbnails), they are the wrong data structure for document generation. However, since the `ApplicationCodeFile` directory is managed by an external team, we treat it as an immutable black box and handle the cropping on our end.

## 2. End-to-End Project Flow

Here is exactly what happens when a user uploads a video on the website:

### Step 1: User Uploads Video (Frontend -> Backend)
* **Frontend**: The user drags and drops a video into the React UI (`src/App.tsx`).
* **Backend**: The Express server (`server.ts`) receives the file via the `/api/process` endpoint.
* **Action**: `server.ts` saves the uploaded file to disk and spawns the Python orchestrator script.
    * **Code**: `server.ts` Line 132 (`const pythonProcess = spawn('python', [...args]);`)

### Step 2: Orchestration Begins (`run_botzilla_local.py`)
* The Express server invokes `run_botzilla_local.py`, passing the video path, task ID, and API keys (`--gemini-key`, `--groq-key`, `--hf-token`).
* This Python script acts as the main director of the pipeline.

### Step 3: Slide Extraction & Cropping
* `run_botzilla_local.py` calls the `extract_slides_ffmpeg()` function (Line 65).
* This function calls out to the external team's code: `vedio_processor.py` inside `ApplicationCodeFile`.
* `vedio_processor.py` runs scene detection, stitches the giant grid, and outputs a `.vtt` file.
* **The Fix**: `extract_slides_ffmpeg()` immediately reads that `.vtt` file, parses the coordinates, and runs FFmpeg crop commands to extract the individual slides back out into a `slides/` directory so we can use them later.

### Step 4: Audio Transcription & Diarization (`audio_engine.py`)
* `run_botzilla_local.py` imports and calls `process_full_audio()` from `audio_engine.py` (Line 494).
* `audio_engine.py` handles the heavy ML lifting:
    * **Transcription**: Uses `whisperx` (Line 101) to transcribe the audio with high accuracy and word-level timestamps.
    * **Diarization**: Uses HuggingFace's `pyannote/speaker-diarization-community-1` (Line 107) to detect *who* is speaking (SPEAKER_00, SPEAKER_01).

### Step 5: AI Summarization (Groq Llama 3.3)
* Still inside `audio_engine.py`, the transcribed chunks are sent to the **Groq API** (Llama 3.3 70B).
* **Chunking**: It breaks the transcript into 1500-word chunks (`process_chunk`, Line 30) to extract action items and fix broken pauses.
* **Master Summary**: It sends the compiled transcript to `gen_master()` (Line 60) to figure out real names for the speakers, extract key decisions, and write an executive summary.
* **Output**: It formats this into a structured UI JSON format.

### Step 6: Merging Slides and Transcript
* Control returns to `run_botzilla_local.py`.
* It takes the `report.json` generated by `audio_engine.py` and maps the previously extracted slides to the exact conversation segments based on overlapping timestamps (Line 538-545).
* It saves the final, combined `report.json`.

### Step 7: Frontend Display
* The Express server detects that the Python process has finished successfully (Exit Code 0).
* It reads `report.json` and sends it back to the React frontend.
* The frontend renders the executive summary, action items, speaker segments, and the inline slides.

### Step 8: Word Document Generation (`docxGenerator.ts`)
* The user clicks the "Download DOCX" button in the React UI.
* This hits the `/api/generate-docx` endpoint in `server.ts`.
* `server.ts` imports `generateDetailedDocxSummary()` and `compileMeetingDocx()` from `docxGenerator.ts`.
* **Action**: `docxGenerator.ts` uses the `docx` npm library to build a highly stylized Word document. It reads the local slide images we extracted in Step 3 and embeds them directly into the document (`Buffer.from(fs.readFileSync(absPath))`). 
* The server streams the final `.docx` file back to the user's browser for download.
